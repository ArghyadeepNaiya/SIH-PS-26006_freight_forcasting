1. Project overview

The user does not tell the system which ship to use. The system tells the user.

A chartering manager enters a cargo requirement. The system returns a ranked set of vessel class and discharge port combinations, each priced as a delivered cost per tonne, together with a recommendation to fix now, wait, or split the cargo.

2. The central insight

A voyage costs approximately the same whether the ship sails full or half full. Therefore the number that matters is total voyage cost divided by the tonnes that can actually be discharged, not divided by the vessel's nominal capacity.

At a draft restricted port these two numbers diverge sharply. Public sources record Haldia with a maximum draft depth of about nine point one metres, accommodating Panamax vessels carrying only forty to fifty percent of capacity. Dhamra is recorded at about eighteen metres of draft and can take super Capesize vessels directly without lighterage.

So a Panamax discharging at Haldia may deliver roughly thirty thousand tonnes while costing close to what a full voyage costs. The freight rate looked cheap. The delivered cost was not.

This single divergence is the product's reason to exist.

3. Four questions the product answers

Everything on screen must serve one of these. If it does not, it gets removed.

  1. Which East Coast discharge port should this cargo come into.
  2. Which vessel class should be chartered.
  3. Should the charter be fixed today, or should the manager wait.
  4. Should this be a single spot fix or part of a longer term contract.

4. Who the user is

A chartering or logistics manager at a steel producer. This person receives a requirement from a plant, for example seventy five thousand tonnes of coking coal needed by mid November. They currently solve it by calling brokers daily.

They are not a data scientist. They will not read a confusion matrix. They will distrust any number they cannot trace to an assumption.

5. Pain points being solved

  1. Daily spot market exploration produces reactive decisions and missed savings.
  2. Freight rates are extremely volatile, so timing a fix badly is expensive.
  3. East Coast ports differ sharply in draft, so the cheapest freight rate is often not the cheapest delivered cargo.
  4. Vessel idle time and demurrage arise from planning that ignores port limits.
  5. There is no structured view of what is actually driving the market.
  6. Procurement is stuck on single spot contracts when the stated objective is to move to short and medium term multiple voyage contracts.

6. Scope

6.1 In scope

  1. Dry bulk and heavy break bulk cargo. Coking coal, thermal coal, limestone, iron ore, manganese ore and steel scrap.
  2. Origins named in the problem statement. Australia, United States, Mozambique, Russia and Indonesia.
  3. East Coast Indian discharge ports. Paradip, Visakhapatnam, Gangavaram, Gopalpur, Dhamra, Haldia and Sagar Sandheads.
  4. Vessel classes. Handysize, Supramax, Panamax and Capesize.
  5. Freight rate forecasting per vessel class with explicit uncertainty.
  6. Port constraint feasibility filtering.
  7. Landed cost per tonne calculation.
  8. Fix now, wait or split recommendation.

6.2 Out of scope

  1. Live vessel tracking. Free global AIS coverage of the Bay of Bengal is limited, so this is not promised.
  2. Actual contract execution or broker integration.
  3. Tanker, container or general cargo trades.
  4. West Coast ports in the first version.

7. The three screens

7.1 Screen 1. Decision Console

Purpose. Produce the answer.

Inputs. Cargo type, quantity in tonnes, origin region, required arrival window, and destination which may be a specific plant or left to the system to choose.

Outputs. A plain English recommendation banner. Three to five ranked option cards showing landed cost per tonne, deliverable tonnes and a one line reason. At least one deliberately shown rejected option with the reason for rejection. An expandable cost breakdown covering freight, port charges, expected demurrage, lightering and inland movement.

7.2 Screen 2. Market and Forecast

Purpose. Make the number on Screen 1 believable.

Contents. Historical rates per vessel class. Forecast shown as a widening band, not a line. A forecast honesty panel stating how much better the model is than assuming tomorrow equals today, at each horizon. Driver attribution. Current market position relative to the last two years.

7.3 Screen 3. Port Intelligence

Purpose. Answer the question why an option was ruled out.

Contents. Each port with maximum draft, length overall, beam and deadweight limits, each value carrying a clickable source citation. Largest vessel class that can berth fully loaded. Loading percentage achievable for larger classes. Congestion and typical waiting days. Lightering availability and cost.

7.4 Non negotiable design rules

  1. One screen produces the answer. The other screens justify it.
  2. Five inputs maximum. Everything else has a default that can be overridden.
  3. Recommendations are in plain language, not a raw confidence number.
  4. Every number on screen is clickable and reveals the assumption behind it.
  5. Every assumption is user editable. A chartering manager knows their own port costs better than the model does.
  6. Uncertainty is always visible. A band, never a bare line.
  7. Where the model has no forecasting skill at a horizon, the interface says so.

8. System architecture

8.1 Architectural principle

The work is split into what runs overnight and what runs when the user clicks. Overnight, the system pulls data, engineers features, retrains models and pre computes forecasts for every vessel class at every horizon. On click, it performs lookups and arithmetic only. This is the decision that makes the demo instant instead of laggy.

8.2 Services

There are three services and one database.

  1. Web. React. Talks only to the Express gateway.
  2. API. Node and Express. Handles requests, persistence, and calls the ML service.
  3. ML. Python and FastAPI. Holds forecasting, constraints, capacity and cost logic.
  4. Database. MongoDB.

React does not call Python directly, because a single entry point keeps request logging, scenario saving and future authentication in one place.

8.3 Nightly batch pipeline

Runs on a schedule, and can also be run manually by command.

  1. Ingest freight rate history for each vessel class from the configured source file or API.
  2. Ingest commodity prices, bunker prices and economic indicators.
  3. Ingest published port position reports to derive a congestion proxy.
  4. Validate and deduplicate. Reject rows outside plausible ranges.
  5. Build the feature matrix. Lags, rolling means, rolling volatility, day of week, month, and exogenous series.
  6. Train the naive baseline, the statistical model and the gradient boosted model.
  7. Evaluate with expanding window time series cross validation. Compute skill score against naive persistence at every horizon.
  8. Persist trained models to disk and forecasts to MongoDB.
  9. Write a run record with timestamps, row counts and metric values.

8.4 Request time pipeline

Target latency under one second.

  1. Candidate generation. Take the cargo quantity and origin. Build every combination of vessel class and East Coast discharge port. Four classes by seven ports gives under thirty candidates.
  2. Hard constraint filtering. For each candidate, check maximum draft, length overall, beam and deadweight against the port constraint record. Mark infeasible candidates as rejected with a stated reason, rather than silently dropping them.
  3. Capacity adjustment. For each surviving candidate, compute the tonnes actually deliverable under two independent ceilings. The weight ceiling comes from deadweight reduced by the draft limit. The volume ceiling comes from the vessel's hold volume divided by the cargo's stowage factor. Whichever is lower binds, and a cargo held by the volume ceiling is said to cube out. Lightering can relieve a weight restriction but never a volume one.
  4. Cost assembly. Look up the pre computed forecast rate for that vessel class over the required arrival window. Add port charges, expected demurrage derived from current congestion, lightering cost where required, and inland movement cost to the destination plant. Divide the total by deliverable tonnes to obtain landed cost per tonne.
  5. Ranking. Sort surviving candidates by landed cost per tonne ascending.
  6. Timing decision. Compare the cost of fixing today against the forecast distribution of cost across the acceptable window. If the expected saving from waiting exceeds the downside risk by the configured margin, recommend waiting. Otherwise recommend fixing now. If a split parcel beats every single vessel option, recommend splitting.
  7. Explanation assembly. Attach the two or three factors that most influenced the answer, plus the assumption set used.
  8. Response. Return one JSON payload containing recommendation, ranked options, rejected options, forecast summary and assumptions.

8.5 API contracts

Express gateway, public. POST /api/recommend.

Request body fields.

  1. cargo_type. String. One of coking_coal, thermal_coal, limestone.
  2. quantity_tonnes. Number.
  3. origin. String. One of australia, usa, mozambique, russia, indonesia.
  4. earliest_arrival. ISO date string.
  5. latest_arrival. ISO date string.
  6. destination_plant. Optional string.
  7. destination_port. Optional string. If absent, the system selects.
  8. overrides. Optional object of assumption overrides.

Response body fields.

  1. recommendation. Object with action, headline, reason and confidence_label. Action is one of fix_now, wait, split.
  2. options. Array of option objects, ranked.
  3. rejected. Array of rejected candidate objects with reason.
  4. forecast_summary. Object with horizon days, forecast band and skill score.
  5. assumptions. Object listing every assumption value used and whether it was defaulted or overridden.
  6. generated_at. ISO timestamp.

Other Express endpoints.

  1. GET /api/ports. Reference data with citations.
  2. GET /api/vessels. Vessel class reference data.
  3. GET /api/rates. Historical series with forecast band, filtered by vessel class.
  4. POST /api/scenarios. Save a scenario.
  5. GET /api/scenarios. List saved scenarios.

ML service, internal only.

  1. POST /ml/recommend. Full pipeline. Called by Express.
  2. POST /ml/forecast. Forecast only, for a vessel class and horizon.
  3. GET /ml/skill. Skill scores by vessel class and horizon.
  4. GET /ml/health.

8.6 MongoDB collections

  1. rate_history. One document per vessel class per date. Fields are vessel_class, date, index_value, tce_usd_per_day, source.
  2. commodity_history. Date, series name, value, source.
  3. congestion_history. Port, date, vessels_at_berth, vessels_at_anchorage, estimated_wait_days, source.
  4. ports. Port code, name, max_draft_m, max_loa_m, max_beam_m, max_dwt, lightering_available, lightering_cost_per_tonne, port_charge_per_tonne, and a citations object holding a source URL for every numeric field.
  5. vessel_classes. Class name, dwt_min, dwt_max, typical_loa_m, typical_beam_m, typical_laden_draft_m.
  6. routes. Origin, discharge port, distance_nm, typical_voyage_days.
  7. cost_assumptions. Key, value, unit, source, editable flag.
  8. forecasts. Vessel class, generated_at, horizon_days, point, lower, upper.
  9. model_runs. Run timestamp, row counts, metrics, skill scores.
  10. scenarios. Saved user inputs and the response returned.
  11. decision_log. Phase two. Recommendation, user decision, later outcome.

Indexes. A compound index on rate_history by vessel_class and date. An index on forecasts by vessel_class and generated_at.

8.7 Reference data strategy

Port constraints, vessel classes and routes live as version controlled JSON files in the repository and are loaded into MongoDB by a seed script, because these values are small, rarely change, and every number needs a source citation that must be reviewable in a pull request. Every numeric field in ports.json carries a matching entry in its citations object. A value without a citation must not be merged.

8.8 Model layer design

Three models, always compared, never one alone.

  1. Baseline. Naive persistence. Tomorrow equals today. This is the number every other model must beat.
  2. Statistical. Seasonal decomposition plus an autoregressive model. Interpretable, fast, and often competitive.
  3. Learned. Gradient boosting, or in the current build, Ridge regression, on lagged and exogenous features.

Evaluation is expanding window time series cross validation, never a random split. Reported metrics are mean absolute error at each horizon, skill score defined as one minus the model error divided by the baseline error, and coverage of the prediction interval. If skill score is not positive at a horizon, the interface must show a no skill banner for that horizon rather than a confident forecast.

8.9 Deployment

Local development runs three processes plus MongoDB. A production demo runs docker compose with four containers. Everything must work with no internet connection once data is seeded, because a live API call during a presentation is an unnecessary way to fail.

9. Requirements summary

Requirement identifiers are stable and are not renumbered as the project evolves.

9.1 Functional requirements

  1. FR-01. The system shall accept a cargo requirement consisting of cargo type, quantity in tonnes, origin region, earliest acceptable arrival date and latest acceptable arrival date.
  2. FR-02. The system shall accept an optional destination plant or destination port. When neither is supplied, the system shall evaluate all East Coast discharge ports.
  3. FR-03. The system shall present no more than five mandatory input fields. All other parameters shall carry defaults.
  4. FR-04. The system shall evaluate every combination of vessel class and discharge port against maximum draft, maximum length overall, maximum beam and maximum deadweight.
  5. FR-05. The system shall mark infeasible combinations as rejected rather than removing them from the response.
  6. FR-06. Each rejection shall state the failed constraint, the port limit value, the vessel requirement value, and the source citation for the port limit.
  7. FR-07. The system shall compute deliverable tonnes for each feasible combination, accounting for draft limited partial loading.
  8. FR-08. The system shall flag whether lightering at anchorage is required.
  9. FR-09. The system shall compute landed cost per tonne as total voyage cost divided by deliverable tonnes, not by nominal vessel capacity.
  10. FR-10. Total voyage cost shall comprise freight, port charges, expected demurrage, lightering cost where applicable and inland movement cost.
  11. FR-11. Every cost component shall be individually visible to the user.
  12. FR-12. The system shall forecast freight rates separately for each vessel class.
  13. FR-13. Every forecast shall be accompanied by a prediction interval, never a bare point estimate.
  14. FR-14. The system shall compute and display a skill score against a naive persistence baseline at every forecast horizon.
  15. FR-15. Where the skill score is not positive at a horizon, the interface shall display a no skill notice instead of a confident forecast.
  16. FR-16. The system shall return exactly one of three recommended actions. Fix now, wait, or split the cargo.
  17. FR-17. The recommendation shall be expressed in plain language, not as a numeric confidence value.
  18. FR-18. The recommendation shall state the two or three factors that most influenced it.
  19. FR-19. Every numeric value displayed shall be traceable to either a data source or a named assumption.
  20. FR-20. Every assumption shall be user editable, and the recommendation shall recompute when an assumption changes.
  21. FR-21. Port constraint values shall display their source citation on demand.
  22. FR-22. The system shall allow a scenario to be saved and retrieved.
  23. FR-23. Phase two. The system shall record each recommendation, the user's actual decision, and the subsequent market outcome.

9.2 Non functional requirements

  1. NFR-01. A recommendation request shall return within one second under demo conditions.
  2. NFR-02. The system shall operate with no internet connection once data is seeded.
  3. NFR-03. The system shall run on a standard laptop. No GPU, no cluster.
  4. NFR-04. Model retraining shall complete within five minutes on the full history.
  5. NFR-05. Every reference data value shall carry a source field. A numeric reference value without a source shall not be merged into the repository.
  6. NFR-06. Forecast evaluation shall use expanding window time series cross validation. Random train test splits are prohibited.
  7. NFR-07. The interface shall never display an accuracy figure without the corresponding baseline figure beside it.

9.3 Data requirements

Required for the prototype.

  1. DR-01. Daily freight rate history for Capesize, Panamax, Supramax and Handysize. Minimum three years, target ten years, with sub indices because vessel selection is inherently a per class question.
  2. DR-02. Port constraint reference data for Paradip, Visakhapatnam, Gangavaram, Gopalpur, Dhamra, Haldia and Sagar Sandheads.
  3. DR-03. Vessel class reference data. Deadweight range, typical length overall, typical beam, typical laden draft.
  4. DR-04. Approximate sailing distances for each origin and discharge port pair.

Desirable, for phase one and two.

  1. DR-05. Commodity price history for coking coal, thermal coal and iron ore.
  2. DR-06. Bunker fuel price history.
  3. DR-07. Economic indicators. An equity index and a dollar index.
  4. DR-08. Published port position reports for congestion.

Data the project will not have, and says so plainly.

  1. DR-09. Actual SAIL fixture history, demurrage records and negotiated port tariffs.
  2. DR-10. Licensed broker data from commercial providers.
  3. DR-11. Forward freight agreement curves.
  4. DR-12. Comprehensive real time vessel positions for the Bay of Bengal.

Consequence. All cost assumptions are drawn from public tariffs, labelled as assumptions in the interface, and user editable.

  1. DR-13. Before any data source is used, its terms of use shall be recorded in data/reference/SOURCES.md together with the date checked and the person who checked it.

9.4 Acceptance criteria for the prototype

  1. AC-01. A user enters seventy five thousand tonnes of coking coal from Australia with an arrival window, and receives a ranked set of options within one second.
  2. AC-02. At least one option is shown as rejected, with the failing constraint named and the port limit cited.
  3. AC-03. A draft limited option displays deliverable tonnes lower than nominal capacity, and the resulting landed cost per tonne reflects the reduced quantity.
  4. AC-04. The cost breakdown expands to show every component.
  5. AC-05. The forecast chart displays a widening band and the skill score against naive persistence.
  6. AC-06. Changing one assumption in the assumptions panel changes the ranking.
  7. AC-07. The entire flow works with networking disabled.

10. Build roadmap

The roadmap is written as a step by step build order for a team of six. A short summary of each step follows. The full detail lives in ROADMAP.md.

  1. Step 0. Hand calculation, data sourcing and reading the domain knowledge, before any code is written.
  2. Step 1. Repository skeleton created exactly as given in the architecture file tree.
  3. Step 2. Reference data written and seeded into MongoDB. Vessel classes, routes, cost assumptions.
  4. Step 3. The constraint engine. Deterministic and testable. Considered the heart of the project.
  5. Step 4. The cost model, checked against the domain lead's hand calculation from step zero.
  6. Step 5. Forecasting, built in order. Baseline first, then evaluation, then features, then the learned model.
  7. Step 6. The decision layer, which must default to fix now whenever forecast skill is absent.
  8. Step 7. The FastAPI service, wiring candidates, constraints, capacity, cost and decision into one handler.
  9. Step 8. The Express gateway, calling the Python service.
  10. Step 9. The Decision Console interface.
  11. Step 10. The Market and Forecast interface.
  12. Step 11. Feature freeze and rehearsal. No new features after this point.

Phase one, after the idea presentation, adds Port Intelligence, congestion ingestion, the editable assumptions panel, a backtested decision policy reported as money saved, and SHAP driver attribution.

Phase two, before the finale, adds contract structure recommendation, parcel splitting optimisation, scenario stress testing, a decision log, a printable export, and verified offline Docker packaging.

11. Current honest status

Running on scaffolding data, the model shows negative skill at almost every horizon. This is correct, not broken. The scaffolding is generated as a near random walk, so there is no signal to find.

The decision engine is hard wired to refuse a wait recommendation whenever skill is absent, and falls back to fix now while stating why. This is the single most defensible thing in the project, and it is not to be removed to make a demo look better.

Independent validation. Given only Haldia's published nine point one metre draft limit and a Panamax's typical laden draft, the capacity model computes a maximum load of forty three point eight percent. Published sources independently state Panamax vessels at Haldia carry forty to fifty percent of capacity. The model was never told this figure, and it agrees with a documented fact it derived from physics.

11.1 Honesty commitments

  1. Freight indices behave close to a random walk at short horizons. A skill score against naive persistence is reported, and the horizons with no skill are published.
  2. Port cost, demurrage and inland cost figures are assumptions drawn from public tariffs, clearly labelled as such, and user editable.
  3. Every port constraint value carries a source citation, because published sources disagree with each other.
  4. No claim is made of real time vessel tracking or licensed broker data.

11.2 Known open items

  1. Plant to port distances are assumptions and need verification against SAIL's annual report.
  2. Most port fields other than draft, length overall and beam are unverified assumptions.
  3. TCE multipliers in the pipeline are placeholders and need replacement with published TCE figures.
  4. The Express gateway and the React app are scaffolded, but the prototype currently runs without them, on the static dashboard alone.

12. How to run this project

  1. From the project root, run ./run.sh.
  2. Open http://localhost:8000 in a browser to reach the working three screen dashboard.
  3. No database is required for the prototype, and no internet connection is required after the first install.

To use real freight rate data instead of scaffolding data, place a CSV file at data/raw/baltic_indices.csv with columns date, BCI, BPI, BSI, BHSI. The loader prefers this file automatically, and the header badge on the dashboard switches from SCAFFOLDING to REAL DATA. Nothing else needs to change.
